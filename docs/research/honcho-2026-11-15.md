## 0. TL;DR

*Written before the decision above. Kelvin chose option B, not the trial of A recommended here. Kept as the reasoning at the time.*

- **Honcho is a service, not a library.** It needs its own API process, a background worker, Postgres with pgvector, Redis, a tool-calling LLM and an embedding model.
- **What it does that our wiki doesn't:** it reads every message Kelvin writes, pulls out single facts about him with links back to the messages they came from, reasons over them while idle to form deductions and patterns, keeps a short "peer card" of key facts, and answers questions about him on demand. Our wiki holds what bots choose to write down; Honcho learns without being asked.
- **Recommendation: run Honcho unmodified on the GPU box as an optional service, behind a `Memory` trait, for a trial.** That is the ponytail answer (reuse before rebuild), it is the only way to use their actual system given the licence, and it is easy to remove. The vault stays the source of truth for anything written down; Honcho adds what was learned.
- **A Rust rebuild inside OrphusBot is possible but is a separate, later decision.** It would be a clean-room job from behaviour described in our own words, and it is months of work to match. Decide after the trial shows which parts earn their keep.

## 1. How Honcho works

### 1.1 The model

- **Workspace:** the root; one per application.
- **Peer:** any participant, human or AI. There is no separate "user" and "agent" type.
- **Session:** one conversation, with any number of peers in it.
- **Message:** something a peer said in a session, or data fed in on a peer's behalf.
- **Conclusion** (stored as a *document* in a *collection*): one thing known about a peer. Collections are keyed by a pair, **(observer, observed)**: what one peer knows about another. A peer's own picture of itself is the pair with both names the same. Which peers observe which is configurable, so a bot only learns from sessions it was in.

### 1.2 The pipeline

1. **Ingest.** Messages arrive through the API (up to 100 a call) and are queued per session, so they are processed in order.
2. **Derive** (the *deriver*, a background worker). Messages are batched by token count. For each observed peer, a model extracts **explicit atomic facts** from that peer's own messages only; what other peers said is context, never evidence. Each fact is one self-contained statement with relative dates resolved, and it records the messages it rests on. Facts are embedded and stored. A counter notes how often the same fact has been derived again.
3. **Summarise.** Each session gets a short summary every 20 messages and a long one every 60 (defaults).
4. **Dream** (the *dreamer*). When a pair has gathered enough new conclusions (50 by default), the session has been idle (60 minutes), and at least 8 hours have passed since the last dream, agents work over the stored facts:
   - a **deduction** specialist creates conclusions that follow from several facts, each recording its premises;
   - an **induction** specialist creates patterns and generalisations, with their sources and a confidence;
   - contradictions between statements are recorded as their own kind;
   - the **peer card**, a short list of key biographical facts, is refreshed;
   - optionally, facts are first sampled by *surprisal* (how unusual a fact's embedding is among its neighbours), and the unusual ones are passed to the specialists as hints.
   Two parts of this are optional settings, reported as off by default at this commit: a fixed budget of tool calls per specialist with the last few reserved for writing (`DREAM.BUDGET_ENABLED`), and working notes the dreamer keeps per pair between dreams (`DREAM.NOTES_MODE`).
5. **Recall**, three ways:
   - **Context** for a session: the summary, recent messages, the representation and the peer card, fitted to a token budget the caller gives.
   - **Chat** (the *dialectic*): ask a question about a peer in plain words. An agent answers using tools: semantic search over conclusions, the reasoning chain behind a conclusion, the messages around it, and semantic, exact-text and date-range search over messages. It has several depth levels.
   - **Conclusions** directly: list, search, create and delete.

### 1.3 How Hermes uses it

Two layers, injected into the **user message** (not the system prompt, so prompt caching survives), inside a fenced block marked as background:

- **Base context**, refreshed every few turns: session summary, the user's representation and peer card, and the same two for the AI itself.
- **A dialectic answer**, every few turns: Honcho's reasoning about the user for the current moment.

Both are cut to a token budget. There is an opt-in mode that does the recall against the current request before the model runs, with a 5-second limit, and drops it on timeout.

### 1.4 What it needs to run

- Two processes (API and deriver), **Postgres with pgvector**, **Redis**.
- An LLM that supports tool calling for four jobs: deriving, summarising, dreaming and the dialectic. Any OpenAI-compatible endpoint works, including vLLM and Ollama. The server refuses to start without one.
- An embedding model (OpenAI's `text-embedding-3-small` by default, 1,536 dimensions; changing the size later is a migration).

## 2. What we have, and the gap

| | OrphusBot today | Honcho |
|---|---|---|
| What gets remembered | What a bot decides to file in the wiki (D-038); Kelvin's own notes in the vault (D-054); Ideas Room recaps | Everything Kelvin says, as facts, without anyone deciding |
| Where a fact came from | The wiki's `raw/` sources | Links to the exact messages, and for deductions, to the premises |
| Reasoning over memory | None | Deductions, patterns and contradictions, formed while idle |
| A short profile of Kelvin | None (the plan's per-bot `notes.md` is hand-kept) | The peer card, kept up to date |
| Asking memory a question | A bot reads wiki files itself | One call, answered by an agent with search tools |
| Who knows what | One shared wiki | Per observer: a bot knows what it was present for |
| Readable and fixable by Kelvin | Yes: markdown in Obsidian | Through its API only |
| Runs on | Nothing extra: files and the bot's own model | Two services, two databases, an LLM, embeddings |

The gap that matters: **OrphusBot never learns about Kelvin unless a bot writes it down.** For an ADHD-first assistant that is the wrong way round. He shouldn't have to repeat how he likes things done.

## 3. Three ways to get it

**A. Run Honcho as it is, beside OrphusBot.** A separate service on the box that the server calls over HTTP.

- For: their real system, working this week; nothing to maintain but a version pin; no licence problem; removable.
- Against: Python, Redis and a second Postgres on the box; four LLM workloads to pay for or host; memory lives in a database Kelvin can't open in Obsidian; anyone else running OrphusBot needs it too, or goes without.

**B. Rebuild it in Rust inside the server.** Our own tables, deriver, dreamer and recall.

- For: one binary, one database, Rust, MIT, our gate and our vault from the start.
- Against: a large build to reach what Honcho does today, and Honcho keeps moving. It must be clean-room: written from §1 of this document, in our own words, with our own prompts. Nothing in their `src/` may be copied or translated.

**C. Take three ideas and put them on the vault.** A nightly routine in which a bot reads the day's threads and writes dated facts about Kelvin into the vault, keeps a one-page profile, and files patterns. Recall is the bot reading those files.

- For: no new service; everything is markdown Kelvin can read and fix.
- Against: it is not their system. No per-message sources, no semantic search, no reasoning chains, and recall quality depends on file layout.

### Recommendation

**A now, as a trial, built so that B or C can replace it.** Kelvin asked for their memory system, and A is the only option that is actually theirs. The `Memory` trait that hard rule "every external system sits behind a trait" already requires is also what makes the choice reversible. Run it for two to four weeks, then look at which of its outputs the bots actually used. If it is mostly the peer card and the facts, C covers that cheaply. If the dialectic answers are what help, keep A or plan B.

## 4. Design for A

### 4.1 Mapping

| Honcho | OrphusBot |
|---|---|
| Workspace | One: `orphusbot` |
| Peers | `kelvin`, and one per bot (its slug) |
| Sessions | One per bot thread; one per discussion; one per Ideas Room conversation; one for deliberate wearable captures |
| Observation | Each bot observes `kelvin`. Bots are not observed, so no model of a bot is built and nothing is spent on it. Revisit if bots should learn about each other |

### 4.2 What is sent, and what never is

- **Sent, after a run ends:** Kelvin's messages and the bot's final replies in that thread, in order, in batches of at most 100 messages (Honcho's limit per call). The cursor of what has been sent moves forward after each batch Honcho accepts, so a long thread is never one oversized call that can't succeed. A server job retries on failure; a Honcho outage never blocks a run.
- **Never sent:** tool calls and results, approval cards and their inputs, secrets and connection details, attachments, other people's speech from ambient capture (DESIGN §10.3), and anything from a bot marked private-scope unless Kelvin turns it on for that bot.
- **Kelvin's switch:** memory is off until `ORPHUSBOT_HONCHO_URL` is set, and each bot has a "learns about you" setting.

### 4.3 How bots use it

- **A short profile at run start.** `team::roster_note` appends Kelvin's peer card, cut to about 1,500 characters. This is the one thing loaded without asking, in line with Kelvin's rule that bots choose what context to load.
- **A `recall` tool.** `recall { question }` opens a dialog the server answers by asking Honcho's chat endpoint as that bot, the same pattern as `ask_bot` and the planned `x_search`. The key and the address stay on the server. It only reads, so the gate lets it through.
- **No automatic injection every few turns.** Hermes does this; we don't, because it spends tokens on every run and works against the context rule.

### 4.4 What Kelvin sees

- A **Memory** screen in the app: the peer card, and the list of conclusions about him, searchable, each with a **Forget** button (Honcho's delete) and the messages it came from.
- **A mirror in the vault:** a nightly job writes the peer card and the newest conclusions to `Memory/learned.md`, read-only, so they show up in Obsidian beside his own notes. Corrections are made in the app, since the file is regenerated.
- This replaces nothing in the Bot HQ plan. The per-bot `notes.md` (plan item 3) stays as the hand-written part: how Kelvin wants a bot to work. Honcho is what was learned.

### 4.5 Running it on the box

- Honcho v3.6.1, unmodified, from its published image, under user-space podman as user units: API, deriver, its own Postgres with pgvector, Redis. Loopback only. Its auth turned on, with the key in a file the server reads.
- **Models.** Subscription logins can't be used: tokens never leave a node (hard rule 4), and Honcho wants an API endpoint. The choices are the box's local model through vLLM, or a paid API key. Local keeps every message on the box. The model must do tool calling reliably, which needs checking against the local Qwen before anything else.
- **Embeddings.** A small local embedding model served on an OpenAI-compatible endpoint, or OpenAI's with a key. The dimension is fixed at first start.
- **Server:** a `memory` module with the `Memory` trait (`record`, `card`, `recall`, `conclusions`, `forget`), a Honcho client over `reqwest`, and a fake in `testkit`. New settings: `ORPHUSBOT_HONCHO_URL`, `ORPHUSBOT_HONCHO_KEY_FILE`. One migration: the per-bot setting and a cursor of what has been sent per thread.

### 4.6 Risks

- **Wrong facts stated confidently.** A deduction about Kelvin can be wrong and then shape every bot. Mitigation: the Memory screen and Forget, and bots are told the profile is background, not instruction.
- **Load on the box.** Deriving and dreaming compete with the bots' own use of the local model. Honcho batches and waits for idle, but this needs watching in the trial.
- **A second copy of personal data.** Honcho's database holds Kelvin's messages. It must be in the box's backups and covered by the same deletion habits; it never goes in the repo (hard rule 8).
- **Upstream changes.** Pin the version; upgrade on purpose.
